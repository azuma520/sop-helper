# 行動追蹤與審核守則

AI SOP 系統所有開發、營運與流程變更皆需對應「行動優先」原則，建立可追蹤的 Action 項目並保留審核留痕。本文件定義共通守則，適用於所有工作階段（規格、實作、測試、部署、回顧）。

## 角色與責任

- **Creator**：負責建立行動項、撰寫描述與完成條件，定義預期輸出。
- **Reviewer**：驗證行動項是否符合憲法原則、檢查輸出品質並留下審核意見。
- **Viewer**：可檢視行動與追蹤狀態，但無法簽核。

行動項建立時必須指定 Creator 與 Reviewer，兩者不得為同一人（若人力不足，需於備註註明原因並於 PDCA 補強）。

## 建立流程

1. **捕捉需求**：於對話、任務清單或程式變更出現時立即記錄 Action，避免口頭或臨時指派。
2. **填寫欄位**：
   - `title`：清楚描述要完成的事項。
   - `owner`：負責執行的成員。
   - `reviewer`：負責審核的成員。
   - `due_at`：預計完成時間（若超過 3 天須補充理由）。
   - `acceptance`：完成條件／核可標準。
   - `links`：相關文檔、PR、任務或規格連結。
3. **分類**：標記至少一個 `domain/role/phase/tool/risk/scope` 控制詞彙，必要時加上 `free` tag。
4. **提交審核**：完成後將狀態調整為 `in_review` 並通知 Reviewer。
5. **結案**：審核通過或記錄豁免後才可將狀態調整為 `done`，並在備註中總結結果或下一步（若需新增行動項，立即建立後關聯）。

## 審核清單

Reviewer 在簽核前需確認：

| 項目 | 說明 |
|------|------|
| 完成條件 | 輸出是否符合 `acceptance` 描述並可驗證？ |
| 憲法原則 | 是否符合五大原則（行動優先、最小可用、持續演化、結構透明、認知節能）？ |
| Artefact 鏈結 | 相關的規格、計畫、程式碼是否更新並附上連結？ |
| 日誌/審計 | 若涉及遮罩、匯出、排程等，是否寫入 AuditLog？ |
| PDCA 追蹤 | 若行動來自 PDCA/週回顧，是否於 PDCA 頁面更新狀態？ |

若審核不通過，需在備註中指出修正項並將任務退回 `pending`。

## 對應工具

- 工單或任務系統（Jira、Linear、Notion 等）需具備上述欄位。
- `docs/guardrails/` 資料夾內可補充各功能模組的審核要點（如 API、UI、資料治理等）。
- 審核要點若需更新，必須建立新行動項並於 PDCA 中追蹤。

## 常見情境

- **多項變更同時進行**：每個可獨立驗證的工作都必須建立行動項；若為同一工作分拆子任務，需保持連結與排序。
- **緊急修正**：仍需建立行動項，但可標記 `risk: high` 並於備註說明緊急原因，事後 24 小時內補上審核紀錄與 PDCA。
- **自動化產生的建議**：AI 產出或排程自動生成的任務必須有人類 Reviewer 確認後才可視為完成。

## 追蹤儀表板

- 根據成功指標，需維護以下度量：
  - 行動完成週期（Created → Done）。
  - 審核退回率（In Review → Pending）。
  - AI 建議採納率與覆核時間。
- 儀表板與警報需託管於 Grafana Cloud（詳見 `specs/001-ai-sop-mvp/plan.md` 與 `tasks.md` 的觀測任務）。

## 版本管理

- 本守則為憲法配套文件，任何修改需透過行動項 + Reviewer 審核後提交。
- 版本號與更新紀錄請於本檔案底部維護。
